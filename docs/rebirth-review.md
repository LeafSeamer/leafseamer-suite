## 1. 审阅结论

### 1.1 已解决的方案冲突

| 编号 | 冲突或遗漏 | 当前稿处理 |
| --- | --- | --- |
| R01 | 曾建议单仓库，用户要求独立仓库 | Organization＋四组件＋Suite；不强制 Submodule |
| R02 | 曾建议继续使用 PostgreSQL | 新版运行库改 SQLite；旧运行现状仍为 PostgreSQL |
| R03 | 保留功能与不迁移旧数据容易混淆 | 保留能力，空库启动；不开发旧数据迁移工具，仅建议文档 |
| R04 | GUI 脱离 NodeCG 与保留图文可能冲突 | GUI 重做，图文通过可选外部 NodeCG 桥接 |
| R05 | 独立 Controller 与统一登录可能耦合 | Q55 已确认指定 Controller 承担套件身份签发；独立本地账户及逐服务授权保留，协议和故障验证仍待落实 |
| R06 | “手动优先”可能只是请求插队 | 持续接管、派发前校验、明确释放、不补发；在途不可取消限制显式记录 |
| R07 | NTP 时间戳可能被误当精确同步保证 | 时间质量可观测，绝对排期门控；不承诺帧同步 |
| R08 | 工作进程和 iframe 可能被误当安全沙箱 | 明确隔离目标，第三方授权及安全设计单列 |
| R09 | 运行库去 PostgreSQL 会误删排期数据源 | 保留外部 PostgreSQL 只读排期导入能力 |
| R10 | 状态机运行中修改与副作用语义未明确 | Q46 已确认固定运行版本及显式切换；状态提交、重试恢复及并行失败由 Q37—Q44 确认，接口与验证待落实 |
| R11 | 排期展示页可能被遗漏 | 排期服务归 Seamer，播出展示经 NodeCG 兼容 |
| R12 | 许可切换可能覆盖原有声明 | 新版主许可与历史／第三方义务分开，不修改旧提交许可 |

### 1.2 审阅通过的边界

- Controller 拥有设备连接与控制；Seamer 拥有自动化，手动和自动动作走同一执行入口。
- API／SDK 与 GUI 解耦；无专用面板也能使用模块能力；SDK 不承担中心服务职责。
- 一个 Seamer、多 Controller、单设备归属，与按服务隔离 SQLite 的方案一致。
- 旧数据免迁移不影响新版自身备份、恢复及后续 Schema 升级。
- 无断网自治不免除连接状态、时间未同步、重启未知结果和同步快照完整性处理。
- 旧 README 保留 NodeCG／PostgreSQL 的历史使用说明，并按新授权增加停止维护及后继项目入口；不得改写成新版已可部署。

## 9. Q50—Q54 已确认

用户已接受以下五项方案，已并入设计稿的决策登记及正文；产品约束确认不代表接口冻结或实现验收。

### Q50：重复触发与竞争转换采用明确仲裁，不积压播出动作

已确认：同一规则默认最多一个活动运行；运行期间的新触发记录为忙碌抑制，不排队、不重启、不覆盖当前运行。状态机转换期间继续更新观测状态，但不接受第二条转换，不在完成后重放期间事件。同一事件命中同一实例的多条可用转换时，按显式优先级选择唯一最高者；最高优先级并列时不执行，暂停该实例并告警，配置预检尽可能提前发现歧义。不同来源的事件按 Seamer 接收序列稳定处理，不把跨来源时间戳当全局顺序。不同规则可独立运行，设备冲突仍由 Controller 仲裁；已有顺序等待必须有界并在派发前复核时效和前提，不能使用无界排队补播。需要连续跟随数值的场景应定义独立的有界控制能力，不借自动重入通用动作实现。

### Q51：设备实际状态与执行前提冲突时暂停相关流程，不自动纠正设备

已确认：动作声明并在流程中确认必要的执行前提，关键播出动作在派发前核对新鲜观测；不沿用早先预检作为永久证据。按当前步骤要求判断，不能把本流程预期产生的变化当异常。外部操作导致必要前提失效或关键状态无法核实时，停止相关后续派发并展示差异；不自动切回旧画面、音量或业务状态。正常声明的外部 Trigger 继续按规则处理，不能把所有外部变化视为故障。已派发动作按在途／未知结果规则处理。无可靠反馈的设备继续遵循 Q38 的显式降级和效果未验证提示，不能伪造前提核实；检查与设备动作之间仍存在竞态，不承诺阻止所有设备外部控制。

### Q52：关键持久化失败时阻止新设备写入，普通日志失败只降级告警

已确认：命令受理及派发所需的关键记录可靠写入后才允许相应阶段继续；关键记录不可写、数据库损坏或关键队列耗尽时，受影响服务拒绝新设备写命令，涵盖自动化及通过该 Controller 发起的手动写入，避免出现不可追踪操作。其他健康 Controller 不因此停用。已派发动作继续尽力观察，未能持久化完成证据时不能报成可靠完成，恢复后查询现状，不重发原命令。状态读取和清晰故障提示尽量保留；普通调试日志或非关键高频遥测写入失败可以限流、丢弃并告警，不单独阻断控制。此决策明确牺牲故障服务的软件写入可用性；现场备用操作依赖设备原生控制台及操作规程，不能假称系统存在安全的无记录旁路。关键记录分类、持久化强度和故障注入属 T08，尚未验证。

存储恢复不自动恢复写入：先验证关键记录可可靠持久化、恢复控制限制并核对未决命令，手动入口通过这些检查后开放；相关自动化还需明确重新布防。

### Q53：模块异常后可有限自动拉起，但只恢复无副作用的连接与采集

已确认：故障模块采用有次数、退避和时间预算的自动重启，超限停止并告警；自动初始化不得重放命令、同步旧目标值或恢复设备预设。不能保证初始化无写副作用的模块禁止自动重启，等待明确处理。重新报告设备身份、能力版本和状态后才算就绪；受影响自动化解除布防，人工核对后明确重新布防，其他健康模块继续工作。手动命令须在就绪并核对接管／未知动作后受理。计划升级、重载或更换驱动必须进入受影响模块的维护流程，处理在途命令后执行，不在直播运行中静默热换。这补充 Q19/Q20 的恢复边界，不改变不续跑、不补发原则。

### Q54：恢复备份、数据库升级及回退只在明确维护状态进行

已确认： Suite 展示并由各服务执行维护门控：暂停受影响范围的新触发与写命令，收集在途结果并明确未决事项后，才允许恢复或数据库变更。维护期间现有设备输出保持原状，不自动黑场或静音；涉及整个服务存储时不能仅维护单台设备。恢复后默认未布防，重新核对身份配对、设备绑定、能力、秘密可用性、接管及未决命令；不执行备份中的旧排期或命令。备份接管记录只作历史依据，不能冒充当前控制权；重新建立有效控制版本，旧客户端身份／待发请求不得因此复活。回退须验证程序、Schema、模块和数据兼容，不能只换旧二进制；升级前备份和恢复演练是发布门槛。普通只读备份可在支持一致性接口时进行，不等于在线多库原子快照，也不要求日常备份打断直播。

恢复演练默认在隔离环境且不连接真实设备；正式替换前确认原实例已经停止控制，不能让恢复副本和原实例同时管理同一设备。备份包含版本清单、配置、数据及秘密恢复所需材料，密钥按既定分离边界管理，不把可解压当作可恢复证据。

### Q55：显式指定一个 Controller 承担套件身份签发

已确认：独立 Controller 使用自身账户；完整套件由管理员指定一个 Controller 提供统一登录与身份签发，Seamer 和其他 Controller 配对信任它，各服务仍独立授权，不新增必需的第六个服务，也不把 Controller 的独立运行绑到 Seamer。首次初始化通过仅部署者可用的一次性流程建立管理员，禁止默认共享口令或公开抢注；配对须核对服务身份、一次性凭证和授权范围，不能凭相同邮箱或用户名自动合并账户。套件普通登录统一走指定签发方，保留受控的本机管理员恢复途径，不能自动退回另一套普通登录绕过撤销。签发方不可用不伪称已登录或已授权；凭据和授权状态不可信时拒绝相关新写入，现场本机恢复仍受接管及关键持久化约束。更换签发方须维护及重新核对信任，不自动选主；这是首期单签发方可用性取舍，后续可通过标准协议适配外部身份提供者，具体协议和库待 T02 审阅。

### Q56：人员会话、权限与设备接管分别管理，撤销需要服务确认

已确认：查看者只读；操作员只可在明确授权范围内控制、接管、布防及恢复，配置编辑／发布、权限管理、配对、维护和紧急接管各有明确权限，不能仅因拥有管理员身份自动抢走设备。登录过期或退出使相应会话的新操作和未派发手动请求失效；账号停用或权限收回更新授权版本，服务在受理及派发前复核，已连接的 WebSocket 同样失去对应权限。自动化授权生命周期按已确认的 Q57 管理。接管保持自动化阻止状态，由仍有权限的人明确转交、接管或释放；在途命令只追踪结果，不承诺撤回。

撤销界面区分签发方已受理与各目标服务已应用，所有相关服务确认前不显示全局生效；未确认目标标为待处理，授权状态超过有效期或无法验证时拒绝相关新写入。远端传播存在窗口，不承诺跨服务原子撤销或零延迟；窗口上限、会话有效期和紧急撤销路径须形成测试标准。增权、配对及凭据管理要求近期重新认证，日常切换画面不反复弹确认。令牌时间校验不得复用可由业务配置任意调整的 NTP 偏移，也不能因“时间未同步”关闭过期检查。

### Q57：自动化使用独立、受限、可撤销的组织授权

已确认：自动化绑定专用服务身份和批准的运行版本，授权限制 Controller、设备、动作及必要参数范围；创建者／编辑者、批准者、布防者和实际执行身份均留审计，不能仅凭编辑权限把服务身份已有的全部能力交给任意规则。发布本身不等于允许执行，布防者只能批准自己有权授出的范围；扩大设备或动作范围、改变批准版本须重新审核授权。人退出、会话到期或账号停用，不隐式撤销已批准的组织自动化，避免人员生命周期意外停播；停用账户时展示其关联自动化，提供显式批量解除布防／撤销入口，人员停用不得被这些额外操作阻塞。组织指定维护责任人，失去可用责任人时告警并要求交接，不能静默转移权限。

服务授权到期、撤销或目标权限收回后，阻止相关新派发、失效待发命令并解除相关布防，已派发仍按在途规则；服务凭据轮换与授权变更分开，有界重叠与旧凭据撤销可追踪，不能因换密钥复活旧授权。密钥及服务凭据不下发 GUI 或扩展面板，独立程序使用自己的受限身份。具体有效期和轮换窗口属于 T02/T09 验证，不能用永不过期管理员令牌代替生命周期设计。

### Q58：排期编辑与外部导入先形成草稿，显式激活未来场次

已确认：手工编辑及 Google Sheets／PostgreSQL 导入先生成草稿及差异，展示来源稳定行身份、版本、时区、动作绑定、删除项和校验错误；不以行号作为稳定身份，不自动按同名合并，也不以空响应或查询失败解释为删除全部排期。用户发布并明确激活后才影响未来尚未受理的场次；激活时服务原子选择旧版或新版，不能靠两个列表各自启动定时器。已受理／派发场次绑定原版本，不在中途换动作；重复导入和仅改标题不得重新触发已执行场次，修改时间也不自动重置已完成身份，需要明确创建新场次才能再次播出。

外部源变化只提出更新，不绕过审批自动改变正在直播的排期。删除或取消未派发场次需明确操作；已派发则展示在途状态并按能力处理，不能把删除行当作设备命令已取消。发布的生效界限和发生版本竞争的结果必须可预览、可审计；临近播出的更改仍遵守前提、布防和截止规则，不悄悄立即执行。排期数据源同步不受此限制停止采集，限制的是更新何时成为可执行计划。

### Q59：区分 UTC 场次与本地日历规则，时区歧义必须显式解决

已确认：一次性场次保存确定的 UTC 时刻，同时保留原本地时间和时区；重复排期保存所选命名时区和日历规则，再生成有稳定身份的具体场次。浏览器／服务器时区变化只影响显示，不改变已批准播出时刻。人工输入不存在或有歧义的本地时间时，不允许静默归一化；需要纠正时间或选择明确的 UTC 偏移。重复规则默认跳过夏令时缺失时刻并显示预览；回拨重复时刻须明确选择其中一次，不默认执行两次。相关政策保存于已发布版本，不留给运行时临时猜测。

时区规则更新影响未来时刻时展示差异，已生成并批准的场次不静默重算；未来受影响场次通过新版本重新确认，无法确定映射的场次暂不允许布防。NTP 向后调整不重置场次执行身份；异常向前跳过的场次记为错过，不补发。失去时间质量仍只门控相关绝对排期，不停止普通手动或单调时钟相对计时。无时区的外部时间必须先明确来源时区，不能默认套用操作者浏览器时区。

### Q60：每个场次有有限派发窗口，区分正常调度延迟和补发

已确认：每个场次拥有稳定执行身份、计划时刻及最晚派发时刻；计划前不得派发，截止后记为错过。有限窗口只容纳持续处于正常布防、授权及时间质量合格状态下的常规调度延迟，不允许无限迟到。若到点时处于暂停、重启、接管阻止、未布防或时间异常状态，该场次立即记为阻止／错过，即使随后恢复仍在窗口内也不补发。正常窗口等待期间一旦门控失效，同样终止该场次派发资格；排队和状态复核不得延长截止。

Seamer 受理或发出 HTTP 请求不等于设备已派发；绝对排期须让 Controller 在接近设备协议发送的门控处再次判断期限及所需时间质量，跨主机不能直接比较单调时间值。窗口约束开始派发，不承诺设备在截止前完成或帧级同步；多步流程每步另有期限和完成标准，只有显式定义的准备步骤可以提前执行。无有效上限的排期不能布防，具体默认值按动作类别和测量确定，允许经预检选择更严格值，不给所有设备拍一个统一毫秒数。晚到但未派发的命令必须被拒绝；已发命令的迟到回执只补充记录，不启动第二次执行。

### 官方依据与本项目选择的边界

- [RFC 7009 第 2.1 节](https://www.rfc-editor.org/rfc/rfc7009#section-2.1) 明确令牌失效可能存在跨服务器传播延迟；Q56 的逐服务确认和派发门控是本项目建议，不代表 RFC 自动提供这些能力，也不代表本轮已选定 OAuth 实现。
- [RFC 5545 第 3.3.5 节](https://www.rfc-editor.org/rfc/rfc5545#section-3.3.5) 区分 UTC 与带时区的本地时间；[第 3.3.10 节](https://www.rfc-editor.org/rfc/rfc5545#section-3.3.10) 规定忽略重复规则产生的不存在本地时间。Q59 的人工歧义确认与已批准场次冻结是本项目建议，不声称完整兼容 iCalendar，也不照搬其对单个日期时间的隐式处理。

### Q61：公共契约按行为兼容，组件、协议及设备能力分别版本化

已确认：区分组件发行版本、公共协议版本及设备能力契约版本；连接时协商协议和必需特性，不能因软件版本号相同就认为兼容。稳定公共契约同一主版本保持向后兼容，新增必填参数、改变单位／默认行为、完成证据、取消或重试语义均须按破坏性变更处理，不能仅以 JSON 字段未变宣布兼容。新增枚举和可选字段也须契约测试证明旧客户端能正确处理；写请求中未知参数应明确拒绝，不能忽略后按意外默认值操作设备。新客户端依赖的特性在旧服务不存在时明确阻止相关操作，不自动选择另一能力。

不兼容时阻止相关写入及自动化，说明所需升级／适配；只有双方明确支持的只读能力才可继续，未知关键结果不能猜成成功。首期服务只提供当前稳定协议主版本，不承诺同时托管多个旧主版本；弃用在兼容版本内公告，移除进入新主版本，安全紧急停止支持须单独公告，不伪装成兼容修复。预发布契约明确不稳定，已发布产物不可原地替换；同一版本产物摘要锁定。SDK 和服务端都校验契约，绕过 SDK 的客户端不能绕过保护；Suite 仅将实测组合列为已验证，不自动升级直播环境。具体支持窗口由发布策略登记，不能用版本号代替验收。

### Q62：并发编辑拒绝覆盖，重复命令与过期身份不能产生新副作用

已确认：规则、排期、设备配置和权限管理提交携带预期修订版本；版本不符返回冲突和可审阅差异，不采用最后写入覆盖，不替用户自动合并影响播出的字段。命令在授权身份、目标和操作范围内绑定幂等身份及规范化请求内容；同身份同内容关联原执行，相同身份不同内容明确拒绝，查询旧结果仍受当前权限约束。重试策略继续遵循 Q40，不因有幂等身份就自动重试写操作。

命令受理有效期、执行详情保留和防重放记录保留是三个独立边界：执行详情清理后可明确返回已清理／不可确认，不能报成从未执行。协议必须定义有界受理期限或服务签发的请求世代，并保证防重放资料至少覆盖全部仍可被接受的身份；缺少足够记录时拒绝不确定旧请求，不能让缓存过期变成新执行。恢复备份也不能重用旧世代。此处只定“过期不复活”的行为，不冻结字段算法；清理策略需证明不会删除仍在运行、未知结果或待审计的必要证据，不要求无期限保存完整日志。

### Q63：API 在受理前限制容量，为控制保护预留处理预算

已确认：服务、身份、设备及扩展分别设置有界请求大小、速率、并发、待发队列和操作时限；批量请求另有限额及逐项结果，不承诺设备级原子批量。超限时在受理前明确拒绝并说明是频率、容量还是服务不可用，不能先报成功再悄悄丢弃，也不把离散控制命令合并为最后一个。已受理命令遵守原执行身份和期限；服务若后来失败必须产生可查询状态，不能无记录消失。限流响应或建议等待时间不构成客户端自动重试写命令的授权，网络超时仍可能是结果未知。

接管、撤销、取消请求及执行查询预留有界预算和适当优先级，避免遥测、批量导入或单个扩展占满正常请求入口；这些入口仍鉴权和限速，不提供公开无限优先队列，不以“高优先级”绕过在途约束。预留容量不绕过 Q52 的关键持久化条件，不保证 CPU、磁盘或设备协议完全故障时仍可接管。调低额度不丢弃既有执行记录，保持过渡期间可解释拒绝；具体默认值、可配置范围及性能目标通过参考环境压测冻结，不能宣传任意服务器可承受无限设备数。

### Q64：高频展示与关键事件分开处理，慢消费者不能拖住控制链路

已确认： API 区分可合并的最新状态／展示遥测与不可静默丢失的命令结果、控制权变化及自动化触发事件。纯展示电平可降频或保留最新值，但参与阈值／边沿触发的数据须声明采样、聚合及丢失语义，触发判断不能依赖 GUI 降采样结果。订阅范围、频率、消息大小和每消费者缓冲均有上限；关键处理路径不能被单个慢订阅者背压阻塞。

慢 GUI 超限后显式告知失步或断开该订阅，重新取带水位快照并核对增量；只令该客户端状态不可信，不因此暂停整个系统。若 Seamer 依赖的事件或执行证据发生缺口，则暂停受影响自动化并核对，不能用当前快照证明缺失期间没有发生事件，也不补放错过动作。短暂重传仅用于明确范围内的传输完整性，不扩展为离线任务补发；权限撤销须在服务端生效，不依赖失步页面及时收到通知。关键记录按持久化／查询契约保留，事件存储和重新同步亦有界，无法恢复完整性时如实告警。

### Q65：第三方面板按固定产物和权限清单批准，实时权限取交集

已确认：第三方面板以明确扩展身份、固定版本／产物摘要和权限清单安装，默认无设备写权限；管理员审阅可读数据、可执行动作、设备范围和外部网络用途，批准安装不自动赋予所有访问者安装者权限。面板有效权限为安装批准范围、当前用户权限及目标服务实时授权的交集；每次请求保留用户与扩展身份，由宿主绑定，面板不能自行声明用户或角色。动作仍走公共受控入口，遵守接管、截止、容量和在途规则，不获得设备秘密、套件签发密钥或长期服务凭据，不在后台替用户布防。

运行在与主 GUI 分离的受限来源，通过校验来源、窗口／通道身份和消息结构的接口请求能力；有敏感数据的消息不用任意目标来源广播。面板本身的网络访问受单独批准和可验证策略限制；仅有 iframe 不代表隔离已安全完成。首期执行代码固定为已批准产物，禁止把会静默变化的远程脚本 URL 当已审阅版本，依赖同样锁定；更新显式启用，权限扩大重新批准，不在直播会话静默换版。卸载、撤销或会话结束阻止该面板新请求并失效相关未派发请求，撤销订阅及临时授权；已派发继续跟踪，接管不自动释放。纯面板卸载不隐式撤销独立组织自动化，但其关联关系应可见。

### Q66：后端模块仅运行管理员明确信任的代码，隔离不等于安全沙箱

已确认：首期 Controller 设备模块、Seamer 数据源及其他后端扩展仅允许管理员明确信任后安装；记录来源、版本、产物摘要、依赖、目标设备、外连用途及所需秘密范围。摘要或签名只支持来源／一致性核验，不能证明代码安全。按现有设计独立工作进程减少故障扩散，但普通宿主进程不能被宣传为恶意代码安全沙箱；不可信插件安全运行及完整操作系统级约束另行设计和验证。

宿主通过 SDK 只授予模块所需设备凭据或引用，不直接开放主库、其他设备秘密和套件签发密钥；确需秘密实现协议的模块只接收其设备范围，声明式权限不能被冒充为已实现操作系统强隔离。无理由不以管理员／root 运行；必须提权的厂商组件明确说明并单独批准。安装包审批与运行授权分开，声明能力不自动取得设备控制权；模块生命周期、调用和自主写入边界须由契约限制并审计。安装、升级、换来源及扩大凭据／外连范围需明确批准，按 Q53/Q54 维护流程处理；卸载前显示依赖并停止相关新派发、处理在途和未知结果，撤销宿主授出的访问，不伪称模块读过的秘密可被“收回”，必要轮换另行安排。
