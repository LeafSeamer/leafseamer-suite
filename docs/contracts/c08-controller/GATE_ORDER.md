# 关闭、恢复与最终有序发送

状态：待审阅的实现边界，沿用137表候选和IPC0.8；不修改已发布机器契约，不新增产品运行实现。

已知事实：既有设计将Controller数据库提交、IPC入流和worker进入设备传输层分开；设备副作用不与SQLite原子提交。CLOSE_GATE只关闸，不转交持有人或核销许可；OPEN_GATE带控制、gate、授权修订及三类拒绝/时间快照，开放确认与ready落库独立。（来源：[F02/F03的I02至I08](../../rebirth-f02-f03-design.md)、[IPC0.8](../df03-service/ipc.schema.json)、[137表关闭通知](PROTECTION_OUTBOX.md)。）

以下为基于上述事实的推荐冻结方案。两端各有独立串行边界，不能用一个“数据库事务成功”代替它们。

## 所有者与字段

| 所有者 | 冻结内容 | 持久/会话边界 |
| --- | --- | --- |
| Controller单writer | ro_attempt原正文、最新目标尝试、ACK验证、一次恢复消费、当前保护与完整恢复记录 | 同库持久；历史记录不因重启改写 |
| Controller会话发送器 | 完整会话身份、每方向seq、未入流候选、单个正在写的帧；每设备dispatch_serial与开放计划 | seq仅入流时分配；队列与serial不跨进程恢复，不作为持久授权代次 |
| 开放计划 | service_boot/运行域、ipc_session、writer_exit、device_session、恢复记录Ref、当前control/gate/authorization版本、barrier及三快照Ref、有限lease | 由当前提供者生成不可变计划；所有Ref完整摘要绑定。任何相关状态改变废弃计划，不能原地替换Ref |
| worker会话 | 严格输入seq、每设备写闸、最新安装屏障、被close作废的开放资格、close_id原正文及原ACK、已消费permit集合 | 握手不打开；缓存丢失终止该会话并关闸，禁止空缓存继续原session |
| 取证/ready提供者 | 原发送帧与reply_to、完整会话/出口、原ACK、当前开放计划、当前存储健康及资源/授权/时间事实 | 只有当前计划仍成立且ACK可靠落库，才发布ready；ACK不是设备动作完成 |

dispatch_serial是本进程内调度防陈旧计数，内部参考模型用整数；线上已有U20/gate_revision语义保持，不能拿serial替代gate_revision。计数溢出关闭会话后重新纳管，不回绕。Controller可由一个连接承载多个设备，但只有该连接发送器写字节和分配seq；设备调度器不能各自持锁后绕过它写同一流。

## 四个顺序点

1. **持久选择**：单writer提交新关闭尝试或恢复。把对应设备serial失效、ready置否与调度通知纳入同一协调临界区；该临界区覆盖提交结果判定和候选登记，不等待网络返回。提交不确定立即锁存存储故障，不继续发OPEN或普通许可。
2. **IPC入流**：发送器在开始一帧前，按当前状态重新选择最新attempt；关闭只取当前设备保护下未完成/需重取证的目标，OPEN只取仍有效的完整开放计划。未开始写的旧候选直接丢弃，不消耗seq；已开始写的帧不可截断插入另帧，也不得放入第二条重试队列。入流与同设备serial改变由同一调度顺序裁决。这里是本机“已选择发送”的点，不证明worker收到。
3. **worker设备写闸**：收到有效新close时，关闭并作废原开放资格；普通/取消设备发送与close、完整屏障、OPEN在同一设备仲裁器排序。已经进入底层调用的字节保留可能已发，后到close不撤回它们。相同close_id/原正文只返回原ACK，即便当前闸已重新开放；同身份异正文触发协议故障、关闭会话。不得把历史ACK解释成当前闸状态。
4. **ACK采用与ready发布**：close ACK先保存历史原件，只有最新目标、正确来源且未被恢复消费的证据可用于新恢复。恢复本身不OPEN；后续安装当前完整屏障、验证全部拒绝/时间快照并取得新gate_revision/token。OPEN_ACK后再次核对完整当前计划与资源，关键事务成功才发布ready。相关状态在任一步改变，旧ACK只留历史，禁止发布ready。

同一已effective操作的重新开闸只推进gate修订，不再次转交持有人；此前close使旧屏障开放资格失效时，必须重新安装当前版本的完整屏障并使用新barrier尝试。完整控制/授权/TIME屏障的持久归并另见收敛清单；本轮不以CLOSE_GATE冒充这些屏障。

## 故障和容量

- OPEN已经入流后才出现新保护：Controller立即撤ready并停止新许可，close排在已入流前缀之后；worker可能短暂收到旧OPEN。此窗口属于传播延迟，不能宣称“本机保护一提交，worker立刻关闭”。之前已入流的许可按实际先后保留在途/未知；新保护后的普通候选不得入流。
- CLOSE尚未入流时产生更新attempt：旧候选不分配seq，新候选使用新close_id；旧尝试已经入流则正常处理历史ACK，不能替新尝试恢复。close与OPEN不可在不同异步队列里独立最终提交。
- 传输部分写、EOF、方向序号缺口或重复原帧：该会话失败关闭，不能跳过字节或从中间重发。逻辑关闭的重投是新信封seq、同close_id/原逻辑正文；只有同一存活会话内可取原ACK。真实缓存保存须先于ACK输出，缓存额度耗尽禁止驱逐仍可能重投的身份后继续原会话。
- 存储失败：独立预留保护容量可发会话内紧急close，不创建虚假incident、durable ACK或ready。普通队列不得占用保护保留量。若当前帧长期阻塞、保护容量耗尽或流不可写，关闭会话并请求监督退役；不得用第二条未排序写通道绕过当前字节流。
- controller范围close覆盖该worker全部已登记设备，每个设备独立关闭后才形成完整ACK；超过单帧容量不能截断。每worker设备上限、ACK实际字节和保护槽保留值归入容量profile，未满足时拒绝新增注册，不能等故障才发现完整ACK放不下。
- Controller崩溃后不重放旧队列、OPEN或设备许可。持久ro_attempt只能作为核对来源；新进程启动先依监督规则关闭/退役旧出口，再以新会话重取当前屏障和关闭证据。worker崩溃/缓存丢失同样不能由新实例证明旧许可未发。新时间域不得复用旧lease。

## 验证与放行

[参考模型](gate_order_model.py)明确区分持久条件、IPC入流、worker接收和ACK采用，用冻结Frame防止排队后正文被改写；模型的资源已清、屏障完整性、当前授权等仍为合成前提，只考察列出的顺序。重启函数假设监督退役已经成立，不执行或证明进程退出；单设备模型不能替代多设备controller范围ACK验收。模型不实现续租、完整业务Guard、数据库或socket。

`check_gate_order.py --report`执行手工预期及有限排列，`--check-report --staged`核验输入字节。真实实现必须按同一验收补充：writer与发送actor竞争、保护插队但不破坏当前帧、部分写及阻塞、缓存上限、主/子进程崩溃、两平台监督退役、完整多设备ACK、lease过期和设备底层隐式重传。全部实际检查完成前不得标注强屏障运行合格。

本轮关闭“最终出口只写串行化原则却没有具体所有者和时序”的设计缺口；实现证明留实施阶段。待归并的具体项目为开放计划到持久control/gate记录的字段映射、完整屏障表、取证提供者及同版SDK语义注册；不能再将整个最终出口设计列为从零建设，也不能用此有限模型宣称它们已交付。
