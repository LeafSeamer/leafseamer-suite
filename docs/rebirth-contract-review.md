## 1. 边界审阅结论

| 编号 | 原表述可能产生的不同实现 | 本轮落实与正反例 |
| --- | --- | --- |
| B01 | 把命令 outcome 当作设备效果或资源锁 | `phase/outcome/effect_status/resource_status` 分开；资源 clear 除明确未发送外必须附 `resource_evidence_ids`，仍需模块验证释放条件；unknown 保持 unresolved。拒绝成功却 not_sent、无证据释放资源 |
| B02 | 条件重试回 queued 后把历史改成“从未发送” | `attempts[]` 保留前次明确失败，命令仍 pending；回 queued 需已有条件重试策略，不能复开 finished。单次尝试的未发不覆盖整个命令历史副作用 |
| B03 | 取消接口返回202被解释成 cancelled | `CancelOperation.requested` 与命令终态分开；cancelled 要求取消确认，设备已开始时仍可有 partial 效果及未清资源。反例拒绝 requested 冒充 confirmed |
| B04 | unknown 后补成功会自动进入下一步 | 原 finished/outcome 保留，`resolution` 追加且 `automation_continuation=paused_latched`；拒绝迟到结果解除暂停及终态重入 queued |
| B05 | pending记录或一个ACK足以报告接管成功 | effective 必须有匹配的 barrier、operation、device、Controller／worker启动身份、控制世代及目标版本，并有生效记录持久化；结构校验加跨字段检查，不能用另一代进程ACK完成本操作 |
| B06 | 接管成功后漏掉此前已发／未知命令 | `BarrierAck` 与操作的 `in_flight_snapshot`／`unresolved_snapshot` 一致；effective可与在途／未知并存，不等于持有人立即能写。缺失清单反例拒绝 |
| B07 | 屏障超时被当失败回滚或旧进程已经退出 | `indeterminate` 仍保护；可以按同一操作／屏障补证据核对，不回滚版本、不复活旧许可。证明旧进程及通道停止前不启动第二个writer |
| B08 | RunGrant请求直接允许自填主体、修订或active | 请求使用 `GrantProposal`，仅提交批准引用与所需范围；主体、revision、state由服务依据认证和已批准定义生成。自填principal/state反例拒绝 |
| B09 | 手动请求伪装automation或反向绕过布防 | automation必须有run_binding，manual禁止携带；请求不能自报principal／role；实际身份及授权匹配仍由服务运行时确认 |
| B10 | Q72的proof revision存在就等于无依赖 | 转换／并行组结构强制required＋stop；顺序可选步骤需要proof引用，但发布必须根据权威能力版本重新验证read/write、守卫、参数及后继影响，客户端声明不构成证明 |
| B11 | 空null、缺字段、单位转换及无限超时各自猜测 | RequestContext、时限联合类型、UTC格式、Revision字符串与非空上限写入Schema；原始JSON检查拒绝重复键及非有限数，未知写字段拒绝 |
| B12 | 同键旧记录可按新能力默认值重新解释 | 原命令保留能力／定义版本、规范化摘要及对应Schema；按原版本比较内容，不能用最新默认值计算后当新命令。过期上下文不创建新执行 |

没有新增需要改变产品目标的选择项。上述字段细化纳入 draft.2；它们并未解除后续实现的证明义务。

## 2. 命令与屏障必须共同满足的顺序

命令生命周期允许条件重试前回到 queued，但仅限**尚未终结的同一逻辑命令**；每次尝试有不同 attempt／permit。`finished` 以后不再向设备发本命令，resolution只是补事实。Controller普通重启不续跑，Seamer恢复不因查询到结果就自动恢复动作链。

最终发送出口对同设备的发送与屏障安装串行排序：

1. 发送先发生：主服务的pending即使已写入，该命令也必须列入在途或未知；不能把旧版本报为未发取消。
2. 屏障先发生：旧版本和旧启动身份的未消费许可失效；其后不得有旧版本设备写。
3. ACK先到但最终事务失败：不报effective，保持保护；ACK丢失也只能核对，不恢复旧队列。
4. ACK和最终事务均可靠成立：报告effective，同时呈现在途／未知；同资源是否允许新手动命令仍按独立资源条件检查。

实现时还要将已持久化 dispatch intent 全部分到“确认未发送”“在途”“未知”之一；不能只核对ACK中出现的条目而忽略不见的意图。许可、ACK不能让模块自行伪造持久化事实，Controller必须将内部候选结果核对、落库后才发布 `CompletionEvidence.durable=true`。

`indeterminate→effective` 是控制权操作的核对进展，允许凭原操作的完整新证据完成；它不等于设备命令 `unknown→重新执行`。服务重启的写闸默认关闭；核对旧ACK只恢复历史事实，当前worker仍须安装有效屏障并确认身份，才允许开放新写入。现有模型轨迹只检查允许的逻辑顺序，真实 IPC 丢包、socket部分发送和进程存活仍属 F02 运行证明。
